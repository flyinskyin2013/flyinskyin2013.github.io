系统实例分析

  此魔改android系统刷机之后的系统发热特别严重，经过htop查看（如下图），发现其cpu7（这个开发板的最大核）内核工作负载极高，但是我们看用户态的cpu的占用，是极少的。下面我们尝试分析一下，为什么内核负载这么高。（这里提前说明，从htop来看，就可以猜是跟gps服务相关，最终结果就是跟这个gps服务有关系，只是形成了连锁反应）

  先使用这个来解锁抓取内核符号地址：

echo 0 > /proc/sys/kernel/kptr_restrict
echo -1 > /proc/sys/kernel/perf_event_paranoid

  然后使用如下命令抓取cpu7的cycle堆栈采用信息：

perf record -c 7 -g -F 99 -- sleep 5

  然后使用如下命令查看当前采样到的堆栈：

perf report --no-children --stdio > perf_data.txt

  通过上面的采样堆栈可知道，大部分的消耗都跑到了如下几个名字的程序上面去了：loc-mq-thread、Ipc-_hub.socket、logd.reader.per、crash_dump64 等，如果对android比较熟悉，我们可以先排除logd.reader.per、crash_dump64 ，因为他们两个是自动dump错误，logcat日志相关的内容（从这里其实可以猜到，有程序在疯狂crash 和 打印日志，logcat也证明了这一点）。

  剩下的两个loc-mq-thread、Ipc-_hub.socket，我们仔细分析后可以发现，loc-mq-thread在疯狂的循环发送接收socket。后面我们需要定位哪些程序会设置这两个线程名字：

  • 首先通过线程名字（/proc/pid/task/tid/comm）得到了对于的pid

  • 通过全局搜索程序、so，查询到loc-mq-thread在/vendor/lib64/libloc_base_util.so和/vendor/lib/libloc_base_util.so，然后通过遍历当前所有进程的映射信息(/proc/pid/maps)，查看哪些程序加载了libloc_base_util.so，然后也得到了一堆pid。

  • 将上面得到的所有pid使用ps来查询，定位出几个程序，他们分别是：

gps           2014     1 0 08:48:48 ?     00:00:02 loc_launcher
gps           5559  5288 0 08:49:02 ?     00:00:00 loc_launcher
gps           2011     1 0 08:48:49 ?     00:00:00 mlid
gps           2311  2014 0 08:48:49 ?     00:00:09 lowi-server

  很遗憾，上面我通过相关查找的时候，会发现一些pid是固定的，一些pid 经常变，这意味着这些pid反复的在创建、退出。这个时候再次引入perf来查看（通过内核在exec的地方埋点，我们可以看到程序启动的一些基本信息），得到了一个有趣的信息：

# sched:sched_process_exec/sched:sched_process_fork可以采集程序通过execve/fork等系统调用时，一些信息
perf record -e sched:sched_process_exec -e sched:sched_process_fork  -a -g -- sleep 5
perf script -G  > perf_data_process.txt

  到这里，我通过抓取execve/fork系统调用，居然一次就找到了我们上面关注的内容，那么可以看到，android.hardware.gnss-aidl-service-qti 反复创建退出（上面其实抓到了多组sched:sched_process_exec: filename=/vendor/bin/hw/android.hardware.gnss-aidl-service-qti），再结合logcat，基本可以确认就是android.hardware.gnss-aidl-service-qti 反复重启导致的。

  由于android.hardware.gnss-aidl-service-qti启动的时候会自动崩溃，但是这个服务会被android的服务管理器自动反复的拉起来，导致了这个坑人的问题。此外，这是android release系统，无法通过adb shell关闭这些服务，经过查询资料，发现了一个新的想法（以前真没这样用过），就是发送STOP信号冻结这个进程，只要进程不退出，android的服务管理就不会反复拉起这个进程。

kill -STOP `pidof android.hardware.gnss-aidl-service-qti`

然后我们再次查看下图，发现我们关心的问题就解决了。后续将这个问题反馈给系统组，由系统组去解决问题即可。





后记

  linux kernel中其实有许多的埋点，可以通过perf的帮助自行查看，通过一些组合命令，可以实现一些不错的效果。例如实时监控系统里面创建哪些程序（名字、路径等等信息）。

  在现在这个时代，已经不是古法排查、古法编程时代了，但是你只要掌握方向，给AI进行提示，依然可以提升你的分析、处理问题的能力。
