前言

  在《Linux程序性能分析（一）—perf原理分析》 https://www.cnblogs.com/Iflyinsky/p/22507762 中，我已经简单分析了perf的工作原理，现在以两篇工作中实际遇到的问题来实际分析。

  先来一篇简单的，可以快速上手的。





通过perf分析用户态的程序

  本示例是一个典型的技术架构设计与实际落地工程实践取舍的问题，具体是：我们自己根据高通提供的参考代码，实现了一版自己的大模型推理程序，并通过http接口暴露了openai api。在客户的实际使用过程中，发现在没有任何http请求时，这个推理程序会莫名的占用200%左右的cpu，具体如下图：

  根据我们之前的经验，直接抓取所有cpu的perf堆栈采样信息，看看到底哪些函数在跑？这次由于我们知道是哪个程序，因此我们直接传入pid来针对程序进行采集：

echo 0 > /proc/sys/kernel/kptr_restrict
echo -1 > /proc/sys/kernel/perf_event_paranoid
perf record -a -g -F 99 -p target_pid -- sleep 5
perf report --no-children --stdio > perf_data.txt

  其实通过上面的堆栈，我们马上就看出来了有线程在死循环，并反复的lock/unlock 这个 std::mutex对象。直接根据符号，查看对应的源码，果然，代码里面，为了kvcache的响应及时性，强行死循环运行，避免了sleep/wait/notify等带来的推理时的开销。其他代码示意如下：

std::mutex mtx;
void ThreadPool::loop()
{
    std::unique_lock<std::mutex> lock(mtx, std::defer_lock);
    while(1){
        lock.lock();

        // do something

        lock.unlock();
    }
}

  最后，根据实际情况，我们没有改变死循环的核心代码，我们采用的方式是，当有推理任务时，通知线程开始死循环运行，既保证了kvcache的实时性，也保证了模型不推理的情况下，资源占用是比较小的。但是在模型推理时，并没有解决死循环带来的cpu空载开销。然后现在我们再看看cpu的占用情况。

  发现在系统空载时，成功解决了问题。
